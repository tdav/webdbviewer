Дата: 2026-08-10 (прогон), стенд владельца проекта.
Приложение: `dotnet run` на `http://localhost:5199`, вход `admin`.
Датасорсы стенда: PostgreSQL «192.168.0.213» (база `postgres`, схема `public` — пустая) и Oracle «token» (схема `TOKEN`, 12 таблиц, 6 подпрограмм).
Проверялось рендером страницы и состоянием приложения, не поиском подстрок в HTML.

## Дефекты, найденные этой проверкой

Оба видны только на живом стенде — ни unit-тесты, ни ревью диффа их не показали.

### 1. После смены датасорса снапшот запрашивался со схемой прежнего датасорса

Переключение с PostgreSQL на Oracle отправляло `GET /api/completion/schema-map?dsId=<oracle>&schema=public`: HTMX перерисовывает фрагмент тулбара асинхронно, и на момент обработки события селект схемы ещё показывал `public` от прежнего датасорса.

Последствия, оба воспроизведены:

- Oracle искал схему `public`, которой в нём нет: запрос отработал **5357 мс** и вернул пустой снапшот. Многосекундная нагрузка на боевую базу при каждом переключении датасорса.
- Пустой снапшот ложился под ключом `<dsId>/public`, а `localCompletions` после перерисовки тулбара спрашивал `<dsId>/`. Промах: локальных подсказок не было вовсе, пока пользователь не выберет схему вручную.

Исправлено в `bb2699a`: при смене датасорса снапшот запрашивается без схемы, серверный `DefaultSchemaFor` подставляет схему по умолчанию нового датасорса. Проверено повторно: запрос уходит как `?dsId=<oracle>` без параметра схемы, локальные подсказки доступны сразу — 12 таблиц.

### 2. Клиент вставлял автоалиас, которого не вставляет сервер

Для `SELECT * FROM |` локальный вариант давал `TV_AGENCYUSERS tvagencyusers`, серверный — `TV_AGENCYUSERS`. Причина: сервер генерирует алиас только при `CompletionOptions.AutoAliasTables`, а это `bool` без инициализатора, то есть `false`, и endpoint зовёт перегрузку без опций. Клиент добавлял алиас безусловно.

Это ровно то расхождение вставки, против которого писался раздел 3.5 спеки: выбор одного и того же варианта до и после серверного ответа давал разный текст.

Исправлено в `bb2699a`: клиентская генерация алиаса и ставший мёртвым порт правила удалены. Проверено повторно: обе стороны вставляют `TV_AGENCYUSERS`.

## Повторный прогон после правок финального ревью

Финальное ревью нашло ещё четыре дефекта; после их исправления сценарии с наибольшим риском проверены на том же стенде (Oracle-датасорс «token»).

| Что проверялось | Факт | Вывод |
|---|---|---|
| Ключевые слова в мгновенной фазе | набрано `sel` → попап сразу содержит `SELF`, `SELECT`, `SELECTIVITY`, `SERIAL`, `SUCCESSFUL` | ✅ раньше ключевых слов в фазе 1 не было вовсе |
| Дубли ключевых слов после серверного ответа | список дорос до 8 вариантов (`BIGSERIAL`, `BASE_TABLE`), повторяющихся элементов — 0 | ✅ дедупликация в `merge` работает |
| Граница слова на квотированном идентификаторе | для `select * from "TV_` локальный `from` = 14 — позиция самой кавычки, как и у серверного пути | ✅ двойной кавычки при вставке не будет |
| Debug-лог длительности интроспекции | при старте: `Интроспекция схемы public датасорса 4f1ecc7d…: 110 мс, таблиц 0` | ✅ |

## Не проверялось

- Поведение при не-первичной базе данных: у Oracle-датасорса выбора баз нет, а на PostgreSQL-датасорсе стенда схема `public` пуста, поэтому сценарий «выбрана не та база → кнопка обновления предупреждает» остался без живого прогона. Логика проверена чтением кода (ревью задачи 9, фикс `49ff3ab`).
- Тёмная тема попапа: эта итерация стилей не меняла.
