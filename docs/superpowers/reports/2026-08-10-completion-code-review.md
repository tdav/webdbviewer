# Ревью диффа: клиентский кэш schema-map для SQL Code Completion

Диапазон: `95acc7e..bd3cc46` (ветка `feature/completion-client-cache`), 14 файлов,
+764/-75 строк в `src`, `frontend`, `tests`. Метод: полный дифф с `-U20` плюс чтение
затронутых файлов целиком (не только хунков) для файлов из риск-листа брифа.
Unit-сюита (373/373) не перезапускалась — по указанию задания.

## Находки (по убыванию серьёзности)

### 1. High — кнопка «Обновить метаданные» не учитывает `isPrimaryDatabaseSelected()`, обновляет не ту базу

**Файлы:** `frontend/src/app.js:369-413` (обработчик клика), `src/WebDbViewer.Web/Pages/Editor/_EditorScope.cshtml:6-34` (кнопка и список схем), `src/WebDbViewer.Web/Pages/Editor/Index.cshtml.cs:280-324` (`OnGetScopeAsync`), `src/WebDbViewer.Web/Services/DbMetadataLoader.cs:23-33`.

**В чём дефект.** `_EditorScope.cshtml` рендерит список схем через `OnGetScopeAsync`, который
открывает соединение с **выбранной в тулбаре** базой (`selectedDatabase`, строка 302: `_connections.OpenAsync(config, selectedDatabase, ct)`)
и получает её реальные схемы (`provider.GetSchemasAsync`). Эта база может отличаться от
`config.Database` (первичной, из настроек подключения) — именно для этого случая существует
`isPrimaryDatabaseSelected()` в `editor.js:380-384`, который блокирует автодополнение целиком
(`editor.js:210`), когда выбрана не первичная база.

Кнопка «Обновить метаданные» (`_EditorScope.cshtml:32-34`) рендерится независимо от того,
первичная база выбрана или нет, и её обработчик в `app.js:369-413` посылает на
`/api/metadata/refresh` только `{ dsId, schema }` — без параметра базы. На сервере
`MetadataRefreshEndpoints.RefreshAsync` → `MetadataCache.InvalidateAsync/WarmupAsync` →
`DbMetadataLoader.LoadAsync` (`DbMetadataLoader.cs:31`) открывает соединение через
`provider.OpenConnectionAsync(config, password, ct)` — **всегда по `config` датасорса**, то
есть всегда к первичной базе, вне зависимости от того, какая база сейчас выбрана в тулбаре.

**Как воспроизвести (подтверждено чтением кода, не требует окружения для демонстрации цепочки).**
Postgres-датасорс с `AllowAllSchemas=true` и несколькими базами в кластере (`Model.Databases.Count > 0`
в `_EditorScope.cshtml:6`). В тулбаре выбрана не первичная база, например `app_reports`
(её `data-primary` не `"true"`, см. `_EditorScope.cshtml:19`). У неё есть схема `public` —
дефолтная схема есть в любой Postgres-базе. Пользователь выбирает схему `public`, жмёт «Обновить
метаданные». Запрос `{dsId, schema: "public"}` уходит на сервер; тот инвалидирует и прогревает
кэш схемы `public` **первичной** базы (`config.Database`), а не `app_reports`, которую видит
пользователь. Пользователь получает тост «Метаданные схемы обновляются» (`app.js`, ветка `res.ok`)
— то есть позитивное подтверждение об операции, которая по факту не затронула нужные данные.

**Предлагаемая правка.** Либо скрывать/дизейблить кнопку через тот же `isPrimaryDatabaseSelected()`-
эквивалент на сервере (не рендерить кнопку в `_EditorScope.cshtml`, когда `Model.SelectedDatabase != Model.ConnectionDatabase`),
либо добавить в `app.js`-обработчик ту же проверку, что уже есть в `editor.js:210`, и не
отправлять запрос / показывать отдельное сообщение «автодополнение недоступно для этой базы».

### 2. Medium — `makeAlias` (JS) расходится с `SemanticCompleter.MakeAlias` (C#) на нелатинских Unicode-цифрах

**Файлы:** `frontend/src/completion-schema.js:76` vs `src/WebDbViewer.Completion/SemanticCompleter.cs:439`.

**В чём дефект.** Граница сегмента в C# определяется через `char.IsDigit(ch)` — это Unicode-
категория `Nd` (Decimal Digit Number), под неё попадают не только ASCII `0`-`9`, но и, например,
арабо-индийские цифры (U+0660–U+0669). В JS-порту та же проверка сделана как
`(ch >= '0' && ch <= '9')` — сравнение по code unit, работает только для ASCII-цифр.

**Как воспроизвели.** Символ `٠` (U+0660, ARABIC-INDIC DIGIT ZERO) — Unicode-категория `Nd`,
то есть `char.IsDigit('٠')` в .NET возвращает `true` (документированное поведение CLR для
категории Nd). Проверено эмпирически в Node.js для JS-стороны:

```
node -e 'const ch="٠"; console.log(ch>=\"0\"&&ch<=\"9\"); console.log(/\p{L}/u.test(ch));'
→ false
→ false
```

То есть для такого символа JS не считает его ни цифрой (граница сегмента не срабатывает), ни
буквой (`\p{L}` тоже `false`, так как `Nd` — не `L`) — символ просто пропускается без изменения
`newSegment`. В C# тот же символ приводит к `newSegment = true` (ветка `char.IsDigit`). Для
идентификатора с таким символом внутри (например, кавычейный идентификатор Oracle/Postgres
`"customer٠orders"`) JS и C# дадут разный алиас: JS не разобьёт сегмент на этом символе, C# —
разобьёт. Расхождение проявляется только для идентификаторов с не-ASCII цифрами внутри — реалистично
редкий, но допустимый (в кавычках) кейс.

**Предлагаемая правка.** Заменить ASCII-диапазон в `completion-schema.js:76` на Unicode-класс,
эквивалентный `char.IsDigit`: `/\p{Nd}/u.test(ch)` вместо `ch >= '0' && ch <= '9'`.

### 3. Low — `serverAnswer` в `editor.js` не инвалидируется при «Обновить метаданные» (узкий кейс повторного ключа)

**Файл:** `frontend/src/editor.js:110, 186, 216-220` vs `frontend/src/app.js:369-413`.

**В чём дефект.** Кнопка обновления метаданных сбрасывает клиентский снапшот через
`window.WebDbCompletion.reset(dsId, schema)` (`completion-schema.js:42-44`), но это трогает
только `cache` в `completion-schema.js`. Переменная `serverAnswer` в замыкании
`makeCompletionSource` (`editor.js:110`) — состояние другого модуля, `reset()` до неё не
дотягивается. Если после обновления метаданных пользователь наберёт **точно** тот же текст и
окажется на той же позиции каретки, что и до обновления (ключ `pos + '|' + текст` совпадёт,
`editor.js:117`), фаза 2 отдаст устаревший ответ сервера, полученный ещё до обновления схемы
(`editor.js:216-220`), — до следующего реального запроса к серверу.

**Почему Low.** Требует точного совпадения полного текста документа и позиции каретки
до и после операции обновления метаданных — на практике маловероятно (нужно набрать/отменить
до идентичного состояния). Не подтверждено воспроизведением, отмечено как «требует проверки»
по методологии брифа, не как подтверждённый дефект.

**Предлагаемая правка (если координатор сочтёт нужным).** В обработчике `refresh-metadata`
(`app.js`) добавить сброс состояния активного `serverAnswer`, либо публиковать в `editor.js`
слушатель на успешное обновление метаданных, инвалидирующий фазу 2 для затронутого редактора.
