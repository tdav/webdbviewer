# Замеры интроспекции Oracle до и после `RESULT_CACHE`

Task 7 плана «Клиентский кэш schema-map для SQL Code Completion». Проверяемый
коммит: `0f9b859` — добавил `/*+ RESULT_CACHE */` в пять словарных запросов
интроспекции схемы Oracle (`src/WebDbViewer.Providers.Oracle/OracleProvider.cs`)
и Debug-лог замера времени в `src/WebDbViewer.Metadata/MetadataCache.cs`.

## Датасорс и окружение

- Датасорс: `token` (Oracle), id `6ce5a9d9-55dc-44a5-a878-684f3d9f69e6`.
- Схема по умолчанию (владелец подключения): `TOKEN`, 12 таблиц.
- Версия Oracle: `Oracle Database 12c Enterprise Edition Release 12.2.0.1.0 - 64bit Production`
  (получена через `SELECT banner FROM v$version WHERE ROWNUM = 1`, выполнено
  через `/api/query/execute` + `/api/query/stream` работающего приложения).
- Метабаза приложения: PostgreSQL `dbviewer_db` (персистентные снапшоты схем
  живут в таблице `webdbviewer.schema_snapshots`).

## Метод замера

Замер делался напрямую через HTTP API приложения, без браузера — это тот же
код, который выполняется при открытии редактора (endpoint schema-map — это
и есть прогрев клиентского кэша автодополнения):

1. Приложение собиралось в изолированный каталог (`dotnet build -o`) из
   отдельного `git worktree` — на своём порту `--urls http://localhost:5107`,
   не трогая основное рабочее дерево (там параллельно работали другие агенты).
2. Перед каждым запуском строка `webdbviewer.schema_snapshots` для датасорса
   `token` удалялась из метабазы — иначе персистентный снапшот (переживает
   рестарт процесса, он лежит в Postgres, а не в памяти и не на диске) отдал
   бы старые данные без обращения к Oracle, и лог интроспекции вообще не
   появился бы.
3. Процесс приложения перезапускался «с нуля» для каждого замера — кэш
   метаданных живёт в памяти процесса.
4. Уровень логирования Debug включался аргументом командной строки
   `--Serilog:MinimumLevel:Default=Debug` (appsettings.json не менялся).
5. Вход в UI — реальный POST на `/login` (admin/admin) с учётом antiforgery
   (скрытое поле, которое `FormTagHelper` вставляет в форму при рендере, а
   не хранится в исходнике `.cshtml`).
6. Триггер интроспекции — обращение к тому же коду, что выполняет открытие
   редактора:
   - **«после»** (текущая ветка, есть `/api/completion/schema-map`):
     `GET /api/completion/schema-map?dsId=<id>` синхронно вызывает
     `IMetadataCache.GetSchemaAsync`, ответ приходит после завершения
     интроспекции.
   - **«до»** (коммит `7188027`, `schema-map` ещё не существовал — добавлен
     позже, в `efaeee9`): использован `POST /api/completion/warmup`,
     единственный на тот момент endpoint, вызывающий тот же
     `IMetadataCache.GetSchemaAsync` через `WarmupAsync`. Это
     fire-and-forget (отвечает `202` до завершения фоновой загрузки),
     поэтому скрипт замера дожидался появления лог-строки поллингом файла
     лога, а не полагался на время HTTP-ответа.
7. Число «до»: в коммите `7188027` Debug-лога интроспекции ещё нет. В
   temporary-worktree (`$TEMP\wdb-before`, никогда не коммитился, удалён
   после замера) в `MetadataCache.LoadCoreAsync` добавлены **дословно те же
   5 строк**, что коммит `0f9b859` внёс в `after` — тот же `Stopwatch`-замер
   вокруг `_loader.LoadAsync(...)` и тот же формат лог-строки. Это гарантирует
   одинаковую границу измерения в обеих сериях: разница между сериями — это
   исключительно наличие/отсутствие `RESULT_CACHE` в тексте SQL, а не другой
   способ засечь время.
8. Число берётся из лог-строки `{ElapsedMs}` (Debug-лог), а не из времени
   HTTP-запроса — так исключается наносекундный шум ASP.NET routing,
   JSON-сериализации и (в «после») HTTP round-trip.

Источник кода замера: `C:\Users\admin\AppData\Local\Temp\claude\...\scratchpad\measure.ps1`
(скрипт временный, в репозиторий не входит).

## Важная оговорка о p95/среднем

Серия «до» содержит два выброса (запуски 1–2, ~2.4 с), а запуски 3–5 — те же
~370–390 мс, что и вся серия «после». Хинт `RESULT_CACHE` тут ни при чём:
причина — обычное кэширование Oracle (buffer cache словарных блоков + shared
pool для уже разобранного текста запроса), которое прогревается после первых
1–2 обращений **независимо** от наличия хинта. Прогрев словарного кэша Oracle
общий для всего инстанса — на нём же в этой сессии параллельно работали
другие агенты, поэтому какой запуск попадёт «холодным», а какой «тёплым»,
зависит от общей нагрузки на сервер, а не от кода.

Серия «после» не показала ни одного холодного выброса только потому, что перед
официальными 5 запусками был один пробный прогон скрипта замера (валидация
пайплайна), который уже прогрел то же самое кэширование для хинтованного
текста запроса. То есть у серии «после» было fore-фору по стартовым условиям,
которой не было у серии «до» — и даже с этой форой медиана «после» не
улучшилась. Поэтому в качестве решающей метрики взята медиана (устойчива к
выбросам с обеих сторон и не зависит от порядка прогрева) — она и является
критерием брифа.

## Вердикт

**Медиана не улучшилась (стала на ~3.6% хуже вместо улучшения хотя бы на
10%) → хинты `RESULT_CACHE` рекомендуется убрать.**

Обоснование:
- Критерий брифа не выполнен: требовалось улучшение медианы ≥10%, по факту
  медиана не улучшилась вовсе.
- Наблюдаемое ускорение в p95/среднем — это эффект обычного кэширования
  Oracle (буферный кэш словарных блоков + shared pool), а не специфика
  `RESULT_CACHE`: серия «до» после прогрева (запуски 3–5) показывает те же
  ~370–390 мс, что и вся серия «после».
- Код без хинтов проще и не занимает место в общем пуле result cache сервера
  (это отдельный пул, за который конкурируют другие сессии/схемы на общем
  инстансе — на этом же Oracle-сервере параллельно работают другие агенты).

  (текущий `HEAD` на момент замера) созданы и удалены (`git worktree remove
  --force`) в рамках этого замера — в истории репозитория не остались.
- Изолированные каталоги сборки `$TEMP\wdb-task7-before`,
  `$TEMP\wdb-task7-after` не входят в репозиторий.
- Основное рабочее дерево не использовалось для сборки/запуска — все
  прогоны шли из изолированных worktree на порту `5107`, отдельном от
  других агентов.
