# Дизайн: ускорение SQL Code Completion (клиентский кэш поверх серверного движка)

Дата: 2026-08-10
Основание: `docs/SQL Code Completion.md` (исследование) + фактическое состояние кода.
Предшественник: `docs/superpowers/specs/2026-08-10-code-completion-design.md` (движок автодополнения, реализован).

## 1. Контекст

Исследование `SQL Code Completion.md` писалось без доступа к репозиторию и это признаёт («диагностика не верифицирована»). Фаза 0 из него выполнена: код прочитан, ниже фактическое состояние.

**Уже реализовано:**

| Пункт исследования | Состояние в коде |
|---|---|
| Серверный движок автодополнения | `WebDbViewer.Completion`: ANTLR + antlr4-c3 (`GrammarAnalyzer`, `CodeCompletionCore`), кэш кандидатов, семантика алиасов/CTE/подзапросов (`ScopeAnalyzer`, `SemanticCompleter`) |
| Контекстные предложения и ранжирование | `Priority.*` в `SemanticCompleter`: колонки контекста → алиасы → таблицы → функции → ключевые слова |
| Авто-alias при выборе таблицы | `SemanticCompleter.MakeAlias` + `CompletionOptions.AutoAliasTables`, коллизии разрешаются по занятым алиасам scope |
| FK-aware `JOIN … ON`, раскрытие `t.*` | реализованы (`Priority.FkRelatedTable`, `RefText`) |
| Tooltip: тип, комментарий, сигнатура | `Detail` / `Documentation` в `CompletionItem`, справочник диалекта `DialectVocabulary` |
| Signature help | `SignatureHelp.cs` + `POST /api/completion/signature` |
| Frecency | `RecentObjects.cs` — LRU на 20 таблиц per datasource |
| Кэш метаданных | `MetadataCache`: TTL, single-flight (`Lazy` + CAS), stale-while-refresh, persistent-снапшот, trie + humps-поиск |
| Прогрев при открытии редактора | `POST /api/completion/warmup` + вызов из `editor.js` |
| Oracle без `DBA_*` | `OracleProvider`: только `ALL_*` с обязательным фильтром `:owner`; версия схемы по `LAST_DDL_TIME` |
| Отсутствие N+1 по колонкам | Интроспекция схемы — 5 batch-запросов (объекты, комментарии таблиц, комментарии колонок, ограничения, колонки) |
| Debounce + отмена | `COMPLETION_DEBOUNCE_MS = 250`, `AbortController`, немедленный путь для Ctrl+Space |

**Не реализовано — это и есть предмет работы:**

1. **Клиентская фильтрация префикса.** Каждая буква после debounce уходит round-trip'ом на сервер — архитектура «Вариант B» исследования, цель p95 < 50 мс недостижима принципиально.
2. **Кнопка «Refresh metadata».** `IMetadataCache.InvalidateAsync` не вызывается из Web-слоя ниоткуда: после DDL подсказки остаются устаревшими до истечения TTL.
3. **`RESULT_CACHE`-хинты** в словарных запросах Oracle.
4. **Замеры латентности** — ни серверных, ни клиентских.

## 2. Решения

| Вопрос | Решение |
|---|---|
| Архитектура | Гибрид **поверх текущего**: серверный ANTLR-движок остаётся источником истины по контексту; клиент получает снапшот схемы и фильтрует локально |
| Масштаб схем | До ~500 таблиц → схема целиком (с колонками) уходит на клиент. **Отдельный lazy-endpoint колонок по таблице не делается** |
| Объём итерации | Скорость + паритет локальных вариантов с серверными. Новой функциональности подсказок не добавляется — она уже есть |
| Тесты | Unit-тесты на новый код. Существующие тесты не переписываются, только чинятся при падении |
| Проверка | Доступны живой PostgreSQL, живой Oracle, запуск приложения в браузере |

## 3. Архитектура: «локально сразу, сервер уточняет»

### 3.1. Endpoint снапшота схемы

`GET /api/completion/schema-map?dsId={guid}&schema={name}` — заменяет `POST /api/completion/warmup` (построение ответа и есть прогрев кэша, отдельный round-trip не нужен).

Источник данных — существующий `IMetadataCache.GetSchemaAsync`; ничего нового из БД не загружается, `SchemaSnapshot` уже содержит колонки, PK, комментарии и routines.

Ответ (короткие ключи — экономия payload; формат внутренний, читаемость не цель):

```json
{
  "schema": "HR",
  "partial": false,
  "tables": [
    { "n": "EMPLOYEES", "t": "table",
      "c": [ { "n": "EMPLOYEE_ID", "d": "NUMBER(6)", "pk": true, "nl": false, "cm": "Табельный номер" } ] }
  ],
  "routines": [ { "n": "GET_SALARY", "t": "function", "s": "(p_id number) return number" } ]
}
```

- `t` таблицы: `table` | `view` | `mview`; `nl` — nullable; `cm` — комментарий, отсутствует если пуст.
- **ETag**: `SchemaSnapshot.VersionHash`, если он не `null`. Запрос с `If-None-Match` при совпадении → `304 Not Modified` без тела: повторное открытие редактора не платит за payload.
- **Порог `partial`**: таблиц > 2000 **или** суммарно колонок > 50 000 → в ответе только имена таблиц (`c` пустой) и `partial: true`. Клиент тогда локально подсказывает лишь имена таблиц, всё остальное берёт с сервера как сейчас. Отдельный lazy-endpoint не вводится.
- Авторизация — как у остальных completion-эндпоинтов (`RequireAuthorization`).
- Схема по умолчанию — существующий `CompletionEndpoints.DefaultSchemaFor`.
- `IMetadataCache.WarmupAsync` **остаётся** (используется в тестах и в refresh) — удаляется только HTTP-endpoint `/api/completion/warmup` и его вызов из `editor.js`.

### 3.2. Клиентский модуль

Новый `frontend/src/completion-schema.js`:

- `load(dsId, schema)` — загрузка снапшота, кэш в `Map` по ключу `dsId + '/' + schema`, дедупликация одновременных запросов (in-flight promise), хранение ETag для последующих запросов.
- `reset(dsId, schema)` — сброс записи кэша (после «Refresh metadata»).
- `localCompletions(ctx)` — варианты из снапшота по грубому контексту (см. 3.3), уже в формате CodeMirror.
- `stats()` — накопленные тайминги локальной фильтрации, для проверки p95.

Экспортируется в `window.WebDbCompletion`, чтобы обработчик кнопки Refresh (другой файл, другой агент) дёргал `reset` без правки `editor.js`.

### 3.3. Грубый контекст на клиенте

Локальный источник не парсит SQL. Достаточно разбора текущего statement регулярными выражениями:

| Ситуация | Что предлагается |
|---|---|
| `alias.` / `table.` / `schema.table.` | колонки соответствующей таблицы (алиасы собираются из `FROM`/`JOIN` текущего statement) |
| после `FROM`, `JOIN`, `UPDATE`, `INSERT INTO`, `DELETE FROM` | таблицы и вью схемы |
| остальное | колонки таблиц из `FROM` текущего statement + таблицы + ключевые слова |

Ключевые слова — встроенным `keywordCompletionSource` из `@codemirror/lang-sql`, свой список не заводится.

Регистр и квотирование идентификаторов повторяют серверное правило `SqlIdentifierQuoting` (Oracle — верхний регистр, PostgreSQL — нижний; кавычки только когда имя не совпадает с нормализованной формой).

### 3.4. Двухфазный источник автодополнения

Один completion source (расширение существующего `makeCompletionSource`), две фазы:

1. **Фаза 1 (мгновенно).** Снапшот есть → возвращаем локальные варианты сразу, попап открывается без сети. Параллельно уходит серверный запрос с текущим debounce 250 мс и `AbortController`.
2. **Фаза 2 (уточнение).** Серверный ответ кладётся в поле состояния с ключом «позиция + текст statement» и вызывается `startCompletion(view)`. На повторном проходе источник видит актуальный серверный ответ для текущей позиции и возвращает объединённый список: серверные варианты первыми (у них точный контекст — CTE, подзапросы, scope, FK-сниппеты), локальные добавляются только те, чьих `label` в серверном ответе нет.

Дубли исключены по построению: объединяет один источник, а не два независимых. Снапшота нет (не загрузился, `partial`, выбрана не основная база) → фаза 1 пропускается, поведение ровно текущее.

Ctrl+Space сохраняет текущий немедленный путь к серверу и дополнительно показывает локальные варианты сразу.

### 3.5. Паритет локальных вариантов с серверными

Локальный вариант не должен отличаться от серверного ни видом, ни результатом вставки — иначе выбор «до 250 мс» и «после» дают разный текст.

- **Алиас таблицы.** Правило `SemanticCompleter.MakeAlias` (инициалы слов имени, при коллизии — суффикс-цифра, занятые алиасы берутся из scope) портируется в JS **буквально**. Отклонение от него — дефект.
- **Kind/Detail/Documentation.** Локальные варианты заполняют те же поля: тип колонки и nullable в `detail`, комментарий в `info`, `type` по той же карте `KIND_MAP`.
- **Приоритеты** соответствуют серверным `Priority.*`: колонки таблиц текущего `FROM` → алиасы → таблицы схемы → routines → ключевые слова.

Проверяется в браузере (батч 2): для одной и той же позиции локальный и серверный варианты одной таблицы дают идентичный вставленный текст.

### 3.6. Refresh metadata

- `POST /api/completion/refresh` `{dsId, schema}` → `IMetadataCache.InvalidateAsync` + фоновый `WarmupAsync`, ответ `202` (тот же паттерн, что у нынешнего warmup: сбой прогрева на редактор не влияет).
- Кнопка в тулбаре редактора рядом с селектом схемы, иконка `UiIcons.Refresh`, тултип «Перечитать метаданные схемы».
- Обработчик клика вызывает `window.WebDbCompletion.reset(...)` и заново грузит снапшот.

### 3.7. Oracle и метрики

- `RESULT_CACHE`-хинты в словарных запросах `OracleProvider` (объекты, колонки, комментарии, ограничения). Эффект замеряется на живой базе до/после — если выигрыша нет, хинты не остаются «на всякий случай».
- Логирование длительности: интроспекция схемы (`MetadataCache.LoadCoreAsync`) и обработка `/api/completion` — уровень `Debug`, в существующий Serilog.
- Клиент: `performance.now()` вокруг локальной фильтрации, накопление в `stats()`; вывод в консоль только при `?debugCompletion=1`.

## 4. Что сознательно не делается

- Lazy-загрузка колонок по одной таблице — при схемах до 500 таблиц лишний слой.
- FK в снапшоте schema-map — FK-сниппеты формирует сервер, и он их уже формирует; на клиенте они не нужны.
- Перенос семантики на клиент (`schemaCompletionSource` вместо ANTLR) — потеря точности на CTE и подзапросах.
- LSP/WebSocket-протокол, AST-парсер на клиенте, JS-тест-раннер.
- `HybridCache` вместо `MetadataCache` — существующий кэш уже даёт single-flight, TTL и stale-while-refresh; замена ради названия из исследования смысла не имеет.

## 5. Критерии приёмки

| Критерий | Как проверяется |
|---|---|
| p95 локальной фильтрации < 50 мс | `window.WebDbCompletion.stats()` на схеме ~500 таблиц |
| Попап открывается без сетевого запроса | Network в браузере: ввод буквы не порождает запроса первые 250 мс, попап уже виден |
| Локальный и серверный вариант вставляют одинаковый текст | ручной сценарий: выбор таблицы после `FROM` до и после прихода серверного ответа |
| Серверные варианты не дублируются локальными | сценарий с CTE и алиасами, проверка списка |
| Повторное открытие редактора → `304` | Network: второй `schema-map` без тела |
| Refresh metadata подхватывает DDL | создать таблицу в живой БД → без Refresh её нет, после Refresh появляется |
| Интроспекция Oracle не медленнее прежней | замер до/после на живой базе |
| Сборка и тесты зелёные | `dotnet build`, `dotnet test` |

## 6. Тестирование

Unit-тесты на новое (`tests/WebDbViewer.Tests.Unit`):

- сериализация snapshot → schema-map DTO: короткие ключи, пропуск пустых комментариев, типы объектов;
- порог `partial` — по числу таблиц и по числу колонок, граничные значения;
- ETag/`304`: совпадение и несовпадение `If-None-Match`, случай `VersionHash == null`;
- `refresh`: после инвалидации следующий запрос идёт в загрузчик (на существующем `FakeMetadataCache` / фейковом `IMetadataLoader`).

Интеграционно (батч 2, живые БД): время интроспекции Oracle до/после, подхват DDL после Refresh.

Клиентский код unit-тестами не покрывается — JS-раннера в проекте нет и вводить его в эту итерацию не будем; проверка браузерная.
