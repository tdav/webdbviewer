# Дизайн: контекстный фильтр мгновенной фазы автодополнения

Дата: 2026-08-11
Предшественники: `2026-08-10-sql-code-completion-design.md` (клиентский кэш schema-map, двухфазный источник).

## Проблема

В мгновенной (локальной) фазе автодополнения ключевые слова диалекта подмешиваются безусловно (`editor.js`, `localResult`): после `SELECT * FROM ` список начинается с `ABORT`, `ABSOLUTE`, `ALTER` — полный словарь диалекта вместо таблиц. Усугубляется перевёрнутым ранжированием: у ключевых слов из `keywordCompletionSource` `boost` не задан (0), у локальных таблиц `boost = −9`, поэтому ключевые слова стоят **выше** таблиц.

Серверная фаза (ANTLR c3) корректна — она возвращает только грамматически допустимые ключевые слова и через ~250 мс поправляет список. Чинится только мгновенная фаза.

## Решение

### 1. Классификатор контекста — `frontend/src/completion-schema.js`

Разбор текущего statement уже есть (`currentStatement`, `tableRefs`, `TABLE_CONTEXT`, квалификатор). Он расширяется до четырёх категорий; категория возвращается наружу: результат `localCompletions` получает поле `context`.

| Категория | Распознавание | Варианты |
|---|---|---|
| `qualifier` | `x.` перед кареткой | колонки таблицы `x` |
| `table` | предыдущее слово ∈ {FROM, JOIN, INTO, UPDATE, TABLE, LATERAL} | таблицы/вью схемы |
| `column` | предыдущее слово ∈ {SELECT, DISTINCT, SET, WHERE, ON, HAVING, BY, AND, OR, WHEN, THEN, ELSE, NOT, IN} | колонки таблиц из FROM текущего statement + функции схемы |
| `general` | всё остальное (начало statement, после `;`, неопознанное слово) | колонки scope + таблицы + функции |

Возврат: `{ from, options, context }`; при пустом списке вариантов, но распознанном контексте — `{ from, options: [], context }` (издателю нужен контекст даже без вариантов, чтобы решить судьбу ключевых слов). Если снапшота нет — по-прежнему `null`.

### 2. Ключевые слова по контексту — `frontend/src/editor.js`, `localResult`

- `qualifier`, `table`, `column` → ключевые слова **не добавляются**.
- `general` → добавляются, каждому варианту проставляется `boost = −19` (ниже приоритета функций −13 и уровня серверных builtin ~−19) — объекты всегда выше.
- Снапшота нет (`localCompletions` вернул `null`) → текущее поведение: только ключевые слова (в т.ч. непервичная база, падение интроспекции).

Двухфазная механика, debounce, `merge`, ключи кэша — не меняются. Сервер не трогается.

## Что сознательно не делается

- Точная грамматика на клиенте (какие ключевые слова допустимы после `FROM` — `LATERAL`, `ONLY`…) — это работа серверного c3, его ответ дополняет список через 250 мс.
- Обработка запятой в SELECT-списке (`SELECT a, |`) — предыдущее слово там идентификатор, категория `general`; сервер уточнит. Отдельного разбора не нужно.
- Изменения ранжирования серверных вариантов.

## Критерии приёмки (браузер, живой стенд)

| Ввод | Мгновенный список |
|---|---|
| `SELECT * FROM ` | только таблицы/вью; `ABORT`/`ALTER`/`AS` отсутствуют |
| `SELECT ` (при `FROM t` ниже) | колонки `t` + функции; без словаря диалекта |
| `WHERE ` | колонки + функции |
| `x.` | только колонки `x` |
| пустая строка + Ctrl+Space | ключевые слова (`SELECT`, `INSERT`, …) |
| `SELECT * FROM t ` (после алиаса) | категория `general`: объекты выше, ключевые слова ниже |

Плюс регресс: серверный ответ по-прежнему объединяется без дублей; в непервичной базе PostgreSQL ключевые слова живы.

## Тесты

JS-раннера в проекте нет (решение прошлой итерации) — проверка браузерная по таблице выше. C#-код не меняется, unit-сюита должна остаться зелёной без правок.
