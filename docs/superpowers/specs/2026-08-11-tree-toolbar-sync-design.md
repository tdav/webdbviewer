# Дизайн: синхронизация дерева навигатора с тулбаром редактора

Дата: 2026-08-11
Предшественники: `2026-08-10-sql-code-completion-design.md` (клиентский кэш, refresh-endpoint), db-aware кэш метаданных, `2026-08-11-completion-context-filter-design.md`.

## Проблема

Клик по датасорсу, базе или схеме в дереве навигатора никак не влияет на тулбар редактора: селекты «Датасорс» (`#editor-ds`), «База» (`#editor-database`), «Схема» (`#editor-schema`) приходится выставлять руками, и автодополнение работает не по тому объекту, на который смотрит пользователь в дереве.

## Требуемое поведение

Клик по узлу дерева одного из трёх типов синхронизирует тулбар и обновляет метаданные:

| Узел | Действие |
|---|---|
| Датасорс (корень) | `#editor-ds` ← датасорс |
| База (PostgreSQL) | `#editor-ds` ← датасорс узла, затем `#editor-database` ← база |
| Схема | `#editor-ds` (+`#editor-database`, если узел внутри базы), затем `#editor-schema` ← схема |

После применения последнего шага — **полный refresh метаданных** (решение владельца: «каждый раз», для Oracle и PostgreSQL): `POST /api/metadata/refresh` + сброс и перезагрузка клиентского снапшота. Повторный клик по тому же узлу — тоже refresh.

Клики по остальным узлам (таблицы, колонки, папки-категории) синхронизацию **не** запускают — иначе каждый шаг по дереву бил бы интроспекцией по базе. Раскрытие/сворачивание узлов не меняется: обработчик синхронизации только наблюдает, `stopPropagation` не зовёт.

## Решение

### 1. Разметка — `src/WebDbViewer.Web/Pages/Shared/_TreeNode.cshtml`

`li.tree-node` сейчас несёт `data-type`, `data-name`, `data-schema`, `data-database`, но не знает своего датасорса. Добавляются:

- `data-ds-id="@Model.DsId"` — на каждый узел;
- `data-tree-role` — только на три типа узлов:
  - `datasource` — корень датасорса (`Model.Path == ""`);
  - `database` — узел базы PostgreSQL (`node.Type == DbObjectType.Database` при непустом `Path`);
  - `schema` — узел схемы (`node.Type == DbObjectType.Schema`).

У прочих узлов атрибут `data-tree-role` отсутствует.

### 2. Синхронизация — `frontend/src/app.js`

Делегированный обработчик клика по `.tree-label` внутри `#nav-tree-root`: ближайший `li[data-tree-role]` даёт роль, `dsId`, имя узла, `data-database`.

Свопы тулбара асинхронные и каскадные: смена датасорса перерисовывает `#editor-scope`, смена базы — перерисовывает его ещё раз. Поэтому целевое состояние кладётся в очередь `{dsId, db, schema}` и применяется пошагово:

1. Если `#editor-ds` отличается — выставить, `dispatchEvent(change)`, ждать `htmx:afterSwap` по `#editor-scope`.
2. Если задана база и `#editor-database` отличается — выставить, `change`, ждать следующий своп.
3. Если задана схема — выставить `#editor-schema`, `change` (схема тулбар не перерисовывает).
4. Вызвать `refreshMetadata(dsId, db, schema)`.

Шаги, где значение уже совпадает, пропускаются (но шаг 4 выполняется всегда). Очередь одна: новый клик по дереву замещает незавершённую очередь предыдущего. Если целевого значения нет в селекте (база/схема ещё не прогрузились в тулбар) — очередь прекращается без refresh, ошибок в консоль не сыпать.

### 3. Одна реализация refresh — `frontend/src/app.js`

Логика существующего обработчика кнопки «Перечитать список таблиц и колонок схемы» выносится в функцию `refreshMetadata(dsId, db, schema)`; кнопка вызывает её же. Две копии правила (кнопка и дерево) запрещены — расхождение копий и есть источник дефектов.

Поведение функции — как у кнопки сейчас: `POST /api/metadata/refresh` с `{dsId, db, schema}`, при `!res.ok` — тост об ошибке без сброса кэша; при успехе — `WebDbCompletion.reset` + `load` + тост. Блокировка от повторного вызова: пока запрос в полёте, новые вызовы игнорируются (сейчас это делает `aria-disabled` на кнопке; при вызове из дерева кнопки может не быть в DOM — блокировка переезжает в функцию, кнопка остаётся визуальным отражением).

## Что сознательно не делается

- Синхронизация в обратную сторону (тулбар → подсветка узла дерева).
- Синхронизация по кликам на таблицы/объекты — только три типа узлов.
- Debounce повторных refresh — владелец явно выбрал «каждый раз».

## Критерии приёмки (браузер)

| Действие | Ожидание |
|---|---|
| Клик по датасорсу `token` в дереве | `#editor-ds` = token; `POST /api/metadata/refresh` в логе сервера |
| Клик по схеме `DICO` под `token` | `#editor-schema` = DICO; refresh с `schema=DICO`; автодополнение предлагает объекты DICO |
| PostgreSQL: клик по базе `asl_belgi_db` | `#editor-ds` = 192.168.0.213, `#editor-database` = asl_belgi_db; refresh |
| Клик по схеме `public` внутри `asl_belgi_db` | `#editor-database` = asl_belgi_db, `#editor-schema` = public; refresh; автодополнение — таблицы `sp_*` |
| Повторный клик по той же схеме | повторный refresh (в логе второй POST) |
| Клик по таблице в дереве | селекты не трогаются, refresh не уходит (открытие данных работает как раньше) |
| Раскрытие узла стрелкой/кликом | работает как раньше |
| Кнопка «Перечитать…» | работает как раньше (через ту же функцию) |

## Проверка при заблокированной сборке

Запущенный из Visual Studio экземпляр владельца не подхватит изменение `.cshtml` (Razor компилируется в сборку) и блокирует `bin/` веб-проекта. Проверка — собственным экземпляром: `dotnet build src/WebDbViewer.Web/DbViewer.App.csproj -o "$env:TEMP\wdb-run"`, запуск `DbViewer.App.exe` из изолированного каталога с `--contentRoot C:\Works\webdbviewer\src\WebDbViewer.Web` и `--urls http://localhost:5199`.
